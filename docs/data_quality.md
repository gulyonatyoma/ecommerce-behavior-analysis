# Data Quality Report

## Подход

Проверки качества данных выполняются до построения продуктовых метрик.

Основной принцип проекта:

> данные исправляются только там, где характер ошибки подтверждён наблюдаемыми данными; в остальных случаях ограничение сохраняется и явно учитывается в аналитике.

В проекте используется реестр `qa.data_quality_rules`, содержащий 17 документированных DQ-правил.

Стратегии обработки:

- `corrected_in_clean` — исправлено в clean layer;
- `excluded_from_trusted_metrics` — сохранено в данных, но исключено из completeness-sensitive метрик;
- `preserved_source_limitation` — сохранено как ограничение источника;
- `diagnostic_only` — используется только как диагностическая информация.

## 1. Exact duplicate events

Exact duplicates определяются по полному набору полей исходного события.

Наблюдаемый excess duplicate count:

| Event type | Excess duplicates | Approx. share |
|---|---:|---:|
| view | 374,449 | 0.10% |
| cart | 858,638 | 4.49% |
| purchase | 151,335 | 2.21% |

Поведение типов событий различается, поэтому глобальная дедупликация не применяется.

### February purchase duplicate incident

Для purchase выявлен подтверждённый временной logging incident примерно с:

`2020-02-10 07:23` → `2020-02-18 06:00`

В этот период наблюдается резкий устойчивый рост exact duplicates purchase-событий.

В clean layer удаляются только exact purchase duplicates внутри подтверждённого incident window.

Удалено:

- **151,087 purchase events**;
- около **2.21% raw purchase events**;
- около **0.037% всех событий**;
- около **$46.75M purchase-event value**.

После исправления:

- raw rows: **411,709,736**;
- clean rows: **411,558,649**;
- raw purchase events: **6,848,824**;
- clean purchase events: **6,697,737**.

Глобальная purchase deduplication не выполняется, поскольку без `order_id`, `event_id` и `quantity` повторяющиеся purchase-события вне подтверждённого инцидента нельзя безопасно признать ошибочными.

## 2. February view/cart logging gap

Подтверждён период:

`2020-02-27 01:00` → `2020-02-28 06:00`

Продолжительность — около **29 часов**.

В этот период объём `view` и `cart` резко снижается, тогда как поток purchase-событий остаётся относительно нормальным.

Интерпретация:

- наблюдаемые события сохраняются;
- отсутствующие события не восстанавливаются;
- период исключается из trusted metrics, требующих полной регистрации view/cart.

## 3. November purchase gaps

Выявлены два периода, в которых purchase-события отсутствуют при продолжающемся потоке view/cart.

### Gap 1

`2019-11-14 18:09:37` → `2019-11-16 08:32:34`

Продолжительность — около **38.4 часа**.

Внутри интервала наблюдалось:

- **8.59M view events**;
- **718.7K cart events**;
- **0 purchase events**.

### Gap 2

`2019-11-16 15:34:30` → `2019-11-17 03:43:18`

Продолжительность — около **12.2 часа**.

Внутри интервала:

- **1.97M view events**;
- **111.6K cart events**;
- **0 purchase events**.

По доступному event log невозможно определить, был ли причиной logging failure или реальная недоступность checkout/payment.

Поэтому purchase-события не импутируются, а интервалы исключаются из соответствующих trusted metrics.

## 4. April purchase logging outage

Последнее purchase-событие перед подтверждённым outage:

`2020-04-19 18:51:12`

Первое событие после восстановления:

`2020-04-22 01:08:20`

Продолжительность — около **54.3 часа**.

Внутри интервала зарегистрировано только **51 purchase event**, что указывает на серьёзную неполноту purchase logging.

Дополнительно вечером 19 апреля наблюдается краткий общий logging disruption.

Обработка:

- существующие события сохраняются;
- purchase не импутируется;
- окна, пересекающие incident period, исключаются из trusted funnel metrics.

Этот инцидент особенно важен при интерпретации апреля, но не объясняет всё снижение conversion: ухудшение View to Purchase наблюдается уже до начала outage.

## 5. User identity conflicts

В source data обнаружены непустые `user_session`, связанные более чем с одним `user_id`.

Найдено:

- **7,037 conflicting sessions**;
- **13,927 affected raw user IDs**;
- максимум **7 user IDs** на один session id.

Распределение conflicting sessions:

| Users per session | Sessions |
|---:|---:|
| 2 | 6,990 |
| 3 | 36 |
| 4 | 6 |
| 5 | 2 |
| 7 | 3 |

Часть пользователей связывает несколько конфликтных session id, поэтому простого pairwise mapping недостаточно.

Используется transitive identity stitching через connected components.

Результат:

- 13,927 affected raw user IDs;
- **6,858 canonical users**;
- maximum identity group size: **7**.

`canonical_user_id` является детерминированным техническим представителем группы и не считается доказанным внешним идентификатором реального человека.

NULL и empty sessions в stitching не участвуют.

## 6. Source session limitations

В данных присутствуют `user_session`, продолжающиеся дни и даже месяцы с большими временными разрывами между событиями.

Поэтому source session id нельзя универсально считать непрерывным визитом пользователя.

Проект намеренно не применяет произвольный inactivity threshold, например 30 минут, для перепостроения сессий.

Session-based выводы, требующие такой интерпретации, не используются как основные продуктовые метрики.

---

## 7. Product/category mapping instability

Связь между `product_id` и категорией нестабильна во времени.

Среди наблюдаемых товаров:

- около **38%** имеют более одного `category_id`;
- около **12%** имеют более одного `category_code`;
- менее **1%** имеют более одного brand.

При этом `category_id -> category_code` внутри наблюдений стабилен.

Массовые product-category изменения концентрируются во времени и выглядят как изменения taxonomy mapping источника, а не как доказанная смена товарной сущности.

Поэтому:

- category сохраняется в event-time состоянии;
- latest-category correction не применяется;
- изменения category mapping не трактуются как реальная смена ассортимента.

---

## 8. Missing taxonomy and brand values

`category_code` и `brand` содержат пропуски.

Они не заполняются искусственно.

NULL `category_code` интерпретируется как невозможность сопоставить исходную категорию с унифицированной taxonomy source dataset.

Missing brand также сохраняется как отдельная наблюдаемая группа.

---

## 9. Zero prices

Negative prices в данных не обнаружены.

Zero price встречается только среди `view` и `cart`.

Такие события сохраняются, поскольку данных недостаточно, чтобы считать их ошибочными.

Для price-band анализа используются только положительные наблюдаемые view prices; отдельные случаи без положительной цены не принудительно относятся к ценовому сегменту.

---

## 10. Trusted metrics

Подтверждённый DQ-инцидент не обязательно означает удаление строк.

Для аналитики используется разделение:

**Observed metrics**
: показывают то, что непосредственно зарегистрировано в event log.

**Trusted metrics**
: дополнительно исключают cohorts/windows, для которых подтверждённый DQ-инцидент нарушает полноту необходимого типа событий.

Таким образом проект не «исправляет» отсутствующие события статистической импутацией, а ограничивает область, в которой метрика считается достаточно надёжной.

---

## Итог

Clean layer изменяет минимально возможный объём данных.

Физически удаляются только exact purchase duplicates внутри подтверждённого февральского logging incident.

Остальные проблемы обрабатываются через:

- сохранение исходных событий;
- DQ flags;
- canonical identity mapping;
- trusted eligibility rules;
- явные ограничения интерпретации.

Это позволяет сохранить наблюдаемый event log и одновременно не выдавать неполные или неоднозначные данные за точные бизнес-факты.
