# Методология анализа

## 1. Принцип проекта

Проект строится по evidence-first подходу: любое исправление данных должно быть подтверждено наблюдаемым паттерном в event log. Если безопасное восстановление невозможно, исходное значение или событие сохраняется, а ограничение явно документируется и учитывается в доверенных метриках.

Базовый аналитический конвейер:

`raw -> qa -> clean -> mart -> dashboard`

- `raw` — исходные события без аналитических исправлений;
- `qa` — диагностические таблицы, подтверждённые инциденты и реестр правил качества;
- `clean` — минимально изменённый event log с доказанными исправлениями и DQ-флагами;
- `mart` — аналитические витрины для продуктового анализа;
- `dashboard` — компактные presentation marts для DataLens.

## 2. Уровень исходных данных

Каждая строка `raw.events` представляет одно наблюдаемое событие пользователя с полями времени, типа события, товара, категории, бренда, цены, пользователя и source session id.

В фактическом датасете присутствуют только события:

- `view`;
- `cart`;
- `purchase`.

События `remove_from_cart` в используемом extract отсутствуют. Поэтому удаление товара из корзины и изменение количества единиц товара не реконструируются.

## 3. Что означает purchase

В extract отсутствуют `order_id`, уникальный `event_id`, `quantity` и итоговая сумма заказа. Из-за этого один `purchase` нельзя доказательно интерпретировать как один уникальный заказ.

В проекте используются следующие формулировки:

- `purchase event` / `purchase-event count` — число зарегистрированных purchase-событий;
- `purchase-event value` — сумма `price` по purchase-событиям;
- `purchasing user` — пользователь с хотя бы одним наблюдаемым purchase-событием.

Не используются как доказанные бизнес-метрики:

- число заказов;
- количество проданных единиц;
- basket size;
- AOV;
- точный GMV / revenue.

`purchase-event value` является наблюдаемым value proxy, а не доказанным GMV.

## 4. Data Quality policy

Для каждого подтверждённого DQ-инцидента выбирается один из четырёх вариантов обработки:

1. `corrected_in_clean` — детерминированное исправление поддерживается доказательствами;
2. `excluded_from_trusted_metrics` — события сохраняются, но период исключается из метрик, требующих полноты;
3. `preserved_source_limitation` — ограничение источника сохраняется без произвольной реконструкции;
4. `diagnostic_only` — аномалия документируется, но сама по себе не является основанием менять данные.

Основной реестр правил хранится в `qa.data_quality_rules`.

## 5. Дубликаты purchase

Exact duplicates анализируются по полному набору полей исходного события.

Для purchase подтверждён ограниченный временной инцидент в феврале 2020 года: резкий и устойчивый рост точных дубликатов, локализованный во времени. Только внутри подтверждённого incident window применяется exact deduplication.

Глобальная дедупликация purchase не выполняется, потому что без `order_id`, `event_id` и `quantity` повторяющиеся строки вне подтверждённого инцидента нельзя безопасно признать ошибочными.

Exact duplicates `view` и `cart` также не удаляются глобально.

## 6. Пропуски логирования

В event log подтверждены периоды частичной потери событий.

Ключевые случаи:

- февральский провал `view` / `cart` при нормальном purchase-потоке;
- ноябрьские интервалы без purchase при продолжающихся view/cart событиях;
- подтверждённый purchase logging outage 19–22 апреля 2020 года;
- краткий общий logging disruption вечером 19 апреля.

События внутри этих периодов не удаляются и не импутируются. Для completeness-sensitive метрик используются явные DQ-флаги и trusted eligibility rules.

## 7. Пользовательская идентичность

Источник содержит случаи, когда один непустой `user_session` связан с несколькими `user_id`. По спецификации источника такой конфликт трактуется как ошибка логирования идентификатора пользователя.

Конфликтные связи объединяются транзитивно. Для каждого connected component создаётся детерминированный `canonical_user_id` — минимальный технический `user_id` внутри группы.

При этом:

- исходный `user_id` сохраняется;
- `canonical_user_id` используется для аналитики пользователя;
- canonical id не интерпретируется как «истинный» внешний идентификатор;
- NULL/empty session не используются для identity stitching.

## 8. Ограничения user_session

Исходный `user_session` не интерпретируется как гарантированно непрерывный визит. В данных присутствуют session id, продолжающиеся дни и месяцы с очень большими временными разрывами между событиями.

Поэтому проект не вводит произвольное правило вида «30 минут бездействия = новая сессия» и не строит ключевые бизнес-выводы на предположении, что source session id соответствует одной непрерывной пользовательской сессии.

## 9. Товары и категории

`product_id -> category_id/category_code` не является полностью стабильным во времени. Наблюдаются массовые изменения маппинга, которые больше похожи на изменения таксономии источника, чем на реальную смену товарной сущности.

Поэтому:

- категория сохраняется в event-time состоянии;
- не применяется `latest category` или `any category` correction;
- NULL `category_code` сохраняется как ограничение source taxonomy mapping;
- изменения категорий не интерпретируются автоматически как изменения ассортимента.

История маппинга диагностируется через `qa.product_dimension_history` и `qa.product_category_history`.

## 10. Funnel methodology

Основная продуктовая воронка строится на уровне `canonical_user_id + product_id`.

Она отражает first-observed event sequence внутри наблюдаемого event log и не доказывает причинный путь пользователя.

Основные trusted показатели:

- View to Cart 1d;
- View to Purchase 1d.

Для оконных funnel-метрик исключаются когорты, чьё окно пересекает подтверждённые периоды неполного логирования соответствующего типа событий.

Поэтому trusted conversion rate — это метрика по eligible cohorts, а не попытка «исправить» отсутствующие события.

## 11. Repeat behavior

Repeat activity определяется как повторное наблюдаемое purchase-событие пользователя в другой календарный день.

Это не эквивалентно доказанному repeat order retention, потому что order-level identifiers отсутствуют.

Для repeat-метрик явно учитывается follow-up coverage. Когорты у границ датасета или рядом с logging gaps могут иметь недостаточное окно наблюдения, поэтому repeat rate всегда интерпретируется вместе с coverage.

## 12. Денежные метрики и price bands

Все денежные расчёты основаны на поле `price`, указанном в USD.

Для price-band анализа используются наблюдаемые положительные view prices. Продукты, которые в течение месяца пересекают границы ценовых диапазонов, не принудительно относятся к одной категории и сохраняются как отдельная группа `Crossed price band`.

## 13. Интерпретация ассортимента

Метрика `not seen previous month` означает только отсутствие наблюдаемого view-события товара в предыдущем календарном месяце.

Она не доказывает:

- добавление нового SKU в каталог;
- удаление SKU из каталога;
- фактическую доступность товара на складе.

Поэтому в dashboard используется термин observed assortment turnover, а не catalog churn.

## 14. April Case Study

Апрельское ухудшение View to Purchase 1d исследуется как диагностический кейс, а не как causal analysis.

Проверены несколько объяснений:

- подтверждённый purchase logging outage;
- product mix;
- price-band mix;
- изменения цен;
- user composition;
- сравнение одинаковых товаров;
- сопоставимые группы пользователей по recency/frequency.

Подтверждённый outage является реальным DQ-инцидентом, но падение conversion наблюдается уже до него. Проверенные mix-effects объясняют только часть ухудшения, а decline сохраняется внутри стабильных сегментов.

Итоговая формулировка проекта: доступный event log не позволяет надёжно приписать апрельское снижение одной наблюдаемой причине. Возможные ненаблюдаемые факторы — availability, delivery conditions, promotions, competition, checkout/payment issues — рассматриваются как гипотезы, а не выводы.

## 15. Что проект намеренно не делает

Проект не:

- восстанавливает отсутствующие purchase-события;
- создаёт фиктивные order ids;
- оценивает units sold без `quantity`;
- называет `sum(price)` точным GMV;
- глобально дедуплицирует purchase;
- насильно нормализует category mapping;
- вводит произвольный session timeout;
- объявляет корреляционные различия причинным эффектом.

Главный методологический принцип: лучше сохранить явно описанное ограничение, чем создать более удобную, но но недоказаемую версию данных.
