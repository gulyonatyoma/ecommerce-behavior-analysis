# Contributing Guide

## Общие правила

Этот документ описывает правила работы участников проекта с GitHub-репозиторием.

Цель:

- сохранить единый стиль разработки;
- упростить командную работу;
- обеспечить понятную историю изменений.

---

# Workflow

В проекте используется следующий процесс:

1. Получить задачу из Jira.

2. Создать ветку от `develop`.

3. Выполнить изменения.

4. Создать Pull Request.

5. Получить review.

6. После одобрения выполнить merge.

---

# Branch Naming

Все ветки должны следовать формату:

тип/EBA-ID-короткое-описание


## Feature

Для новых задач:

Пример:

feature/EBA-12-funnel-analysis


## Fix

Для исправления ошибок:

Пример:

fix/EBA-25-data-error


## Documentation

Для документации:

Пример:

docs/EBA-30-readme-update

---

# Commit Messages

Коммиты должны быть короткими и понятными.

Хорошие примеры:

add customer segmentation analysis

update data dictionary

fix missing values handling

Плохие примеры:

test

changes

update

---

# Pull Requests

Каждый Pull Request должен содержать:

- ссылку на Jira задачу;
- описание изменений;
- список проверок;
- дополнительные комментарии при необходимости.

---

# Code Review

Перед merge необходимо:

- проверить изменения;
- убедиться, что код работает;
- проверить отсутствие лишних файлов;
- убедиться, что документация обновлена при необходимости.

---

# Работа с данными

Запрещено:

- добавлять большие датасеты в GitHub;
- изменять файлы в `data/raw`;
- добавлять персональные данные.

---

# Работа с ноутбуками

При добавлении Jupyter Notebook:

Необходимо:

- очистить лишний output;
- добавить понятное название;
- описать цель анализа;
- сохранить воспроизводимость.

---

# Стиль разработки

Рекомендуется:

- писать понятный код;
- добавлять комментарии при сложной логике;
- использовать переиспользуемые функции;
- не дублировать код.
